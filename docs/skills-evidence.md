# Skills evidence

Source: <https://github.com/mattpocock/skills> (MIT, © Matt Pocock).
Installed copy: `.opencode/skills/` (12 skills + license file).

The installer (`npx skills add`) needs `git`, which is not installed on this
machine, so the same repository was downloaded as a tarball and the relevant
skill folders were copied into the project. OpenCode discovers
`.opencode/skills/<name>/SKILL.md` automatically.

## Which skills shaped this build

| Skill | How it was used | Artifact you can open |
| --- | --- | --- |
| **grilling** | Interviewed the student on scope, DB, roles, and deliverable order before writing code (4 questions, recorded verbatim). | `docs/prompts.md` §1, answers in §2 |
| **grill-with-docs** | Same interview, plus the convention of writing the shared language and decisions down while they are fresh. | `docs/GLOSSARY.md`, `docs/adr/0001–0003` |
| **to-spec** | Synthesised the PDF + interview into a spec with explicit non-goals and acceptance criteria. | `docs/spec.md` |
| **to-tickets** | Broke the spec into tracer-bullet tickets with blocking edges and honest status (T9 open). | `docs/tickets.md` |
| **implement** | Built one vertical slice per ticket: schema → query → action → UI → verify. | `actions/`, `lib/queries.ts`, `app/(app)/*` |
| **codebase-design** | Chose one deep read module (`lib/queries.ts`) and thin actions; no page builds SQL. | `lib/queries.ts`, ADR 0002 |
| **domain-modeling** | Fixed the vocabulary (record ≠ absent, time in is a DB fact, rate definition). | `docs/GLOSSARY.md`, `docs/erd.md` |
| **code-review** | Two-axis review of the finished tree: Standards (types, lint, build, security smells) and Spec (acceptance criteria). | `docs/review.md` |
| **writing-for-agents** | README/AGENTS.md shaped so the next agent can find the setup, vocabulary, and verification commands. | `README.md`, `AGENTS.md` |
| **tdd** | **Not used — not claimed.** No automated test suite exists; ticket T9 records it as open. | `docs/tickets.md` T9 |

## What was agent-generated vs skill-guided vs human-verified

| Layer | Owner |
| --- | --- |
| Schema, queries, actions, UI, docs drafts | Generated by the agent in this session |
| Workflow order, spec/ticket/ADR formats, module boundaries | Guided by the skills above |
| Understanding and defense | **You** — open every file, run the demo, and change something yourself |

The PDF explicitly warns: *"Do not claim a skill generated files if it did not."*
This table is written to that rule. `tdd` is listed as unused on purpose.

## Suggested proof sequence for the panel

1. Open `.opencode/skills/` in the editor and show the installed `SKILL.md`
   files (e.g. `to-tickets/SKILL.md`).
2. Open `docs/prompts.md` and point at the exact questions/answers that changed
   the build (single admin, local Supabase, basic scope).
3. Show the artefacts those skills produce: spec → tickets → code → review.
4. Run `npm run typecheck && npm run lint && npm run build` live.

## Reproduce a genuine skill run

```bash
# if git is available
npx skills@latest add mattpocock/skills -a opencode

# then, in OpenCode
/grill-with-docs      # re-interview and regenerate GLOSSARY + ADRs
/to-spec              # regenerate docs/spec.md from the conversation
/to-tickets           # regenerate docs/tickets.md
/implement            # work the tickets with TDD at pre-agreed seams
/code-review          # two-axis review before committing
```

If the panel asks "which skill influenced what?", answer with the table above,
then show the files — not a claim that a skill wrote code by itself.
