 PART 7 - Q&A BANK (answer in 2-3 sentences, then offer the file)
================================================================================
 Q  Why App Router?
    Server Components render the roster next to the data; server actions give
    mutations a typed server boundary with no hand-written API routes.
    -> app/(app)/attendance/page.tsx, actions/attendance.ts

 Q  Where is auth enforced?
    Three layers: proxy refresh, requireAdmin() as the real gate, RLS as the
    database guarantee.
    -> proxy.ts, lib/auth.ts, migration

 Q  Why security definer on is_admin()?
    profiles only lets a user read their own row; without definer the policy's
    own check gets filtered by RLS and returns false. search_path is pinned
    against schema hijacking.

 Q  Isn't shipping the anon key dangerous?
    It identifies the project, it does not authorize. With no session every
    table returns zero rows - I can show you that. service_role bypasses RLS and
    lives only in a gitignored env file for a local script.

 Q  How do you know the timestamp is real?
    The form never sends it. A trigger stamps now() on insert, only when null,
    and a CHECK refuses present/late without it.

 Q  What if the teacher clicks Present twice?
    Upsert on (student_id, attendance_date). Same row updated, timestamp
    unchanged, no duplicate. A second row for the same day is a 409.

 Q  Where is validation?
    Zod in every action, and the same rules again as enums, CHECK, UNIQUE and
    FKs in Postgres. Client attributes are convenience only.

 Q  Why only one admin role?
    Recorded scope decision in ADR 0003. Multi-role needs section ownership and
    narrower policies; the schema already supports adding it.

 Q  Walk me through marking present, end to end.
    Form POST -> action -> requireAdmin -> Zod -> upsert -> trigger stamps ->
    constraints and RLS -> revalidatePath -> server re-render.

 Q  Duplicate LRN?
    Postgres raises 23505, the action maps it to a field error, nothing inserts.

 Q  Are there tests?
    No - ticket T9 is open, and I will not claim otherwise. What I do run:
    typecheck, lint, production build, a schema verification script that replays
    the migration in an in-process Postgres, and a manual smoke test of all four
    statuses plus the duplicate-day rejection.

 Q  What breaks first at scale?
    The attendance page loads a section's roster and counts in JS. At thousands
    of rows that moves to SQL aggregation - the summary view already exists.

 Q  What did the AI get wrong?
    Session pages prerendered statically; proxy crashed when Supabase was down;
    and the two integration bugs I described - NULL token columns and the
    email-provider flag. Each one found by running it.

 Q  Which skill changed a decision?
    grilling forced the four scope questions before code. to-tickets forced the
    vertical-slice order. codebase-design produced the single read module. None
    of them wrote the code.

 Q  What is NOT implemented?
    Teacher accounts, subjects/grading, parent access, notifications, uploads,
    realtime, automated tests. Say it before they find it.

 Q  How would you deploy this for real?
    Run the migration on hosted Supabase, create the admin through the dashboard
    or a service-role script, set three env vars, keep signup disabled. No code
    change - only environment. I actually tested that path end to end.

 Q  Why is Docker required - why not just the cloud?
    The guidelines require a self-hosted Supabase in Docker, and it also means
    the demo works offline. The hosted copy exists as a backup and as proof the
    schema deploys elsewhere.
